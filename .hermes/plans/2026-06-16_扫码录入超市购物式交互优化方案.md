# 扫码录入“超市购物式”人机交互优化方案

## 一句话目标

把扫码录入从“扫一个码→跳页面→填数量→提交→返回”改成“像超市收银一样连续扫码→形成待处理清单→逐行校验/改数量→统一提交→异常单独处理”。

## 核心设计原则

1. **连续不中断**：扫码枪/手机扫码识别后只入清单，不跳转、不弹大窗阻断。
2. **默认帮人填好**：系统自动带出可录入数量、工序、厂家、动作类型，操作员只改异常项。
3. **异常后置处理**：有效码继续扫，无效/无权限/不可操作码进入异常区，不打断主流程。
4. **一眼可确认**：每行用颜色、图标、状态文案区分“可接收/可发出/仅查看/异常”。
5. **少输入、多确认**：现场操作员主要动作是“扫、看、改数量、提交”。

## 推荐页面结构

### 顶部：工作状态区

- 标题：扫码录入
- 当前模式：扫码枪 / 手机相机 / 拍照识别
- 统计：
  - 已扫数量
  - 可提交数量
  - 异常数量
  - 本次预计接收/发出总数
- 明显提示：`连续扫码中，扫到码会自动加入下方清单`

### 中部：扫码输入区

#### 扫码枪模式

- 一个大输入框，始终自动聚焦。
- 回车即入清单。
- 扫完后输入框自动清空并重新聚焦。
- 不跳转页面。

#### 手机扫码模式

- 相机预览区。
- 中央扫描框。
- 成功识别后：震动/提示音/轻 toast，自动加入清单。
- 继续保持相机开启，可扫下一张。
- 增加“暂停扫码 / 继续扫码”。

#### 兜底入口

- 拍照识别。
- 相册识别。
- 手工输入二维码编号。

### 下部：录入清单区（核心）

每一行类似超市购物小票/购物车：

- 左侧：动作标签
  - 蓝色：接收
  - 绿色：发出
  - 灰色：查看
  - 红色：异常
- 主信息：
  - 订单号 / 工序名 / 厂家
  - 二维码简写
  - 可操作原因或异常原因
- 右侧：数量编辑
  - 默认填 `available_receive_qty` 或 `available_ship_qty`
  - 支持 `- / +` 步进
  - 支持手输
  - “全部”快捷恢复默认可用数量
- 行操作：
  - 删除
  - 查看详情
  - 异常项重试

## 推荐交互流程

### 流程 A：正常连续扫码

1. 操作员进入扫码录入页。
2. 页面默认聚焦扫码枪输入框。
3. 操作员连续扫二维码。
4. 每扫一次，下方清单新增一行。
5. 系统自动判断：接收/发出/查看/异常。
6. 系统自动填默认可用数量。
7. 操作员只检查数量，有需要就改。
8. 点击底部“提交 X 条”。
9. 系统逐条提交，并在原行展示成功/失败。
10. 成功项自动折叠或进入“已完成”区，失败项保留在清单顶部。

### 流程 B：扫码中遇到异常

1. 扫到无效码/无权限/数量为 0。
2. 不弹阻断框。
3. 该码进入异常区，红色标记。
4. 页面轻提示“1 条异常，已放入异常区”。
5. 操作员继续扫码。
6. 扫完后统一处理异常。

### 流程 C：批量提交失败

1. 点击统一提交。
2. 成功项显示“已提交”。
3. 失败项保留为“待处理”。
4. 失败原因直接显示在行内。
5. 支持单行重试 / 删除 / 查看详情。

## 关键页面细节建议

### 1. 数量输入优化

不要只放普通输入框，建议改为：

- `-` 按钮
- 数量输入框
- `+` 按钮
- `全部` 按钮
- 超量时实时红字提示：`不能超过可接收 80`

### 2. 扫码反馈优化

每次成功扫码应有即时反馈：

- 成功加入：短震动 + 绿色轻提示
- 重复扫码：黄色提示，并定位到已有行
- 异常码：红色提示，但不阻断继续扫码

### 3. 重复扫码处理

推荐策略：

- 同一二维码重复扫：不新增行，定位已有行并闪烁。
- 如果业务允许分批同一记录多次录入，可提供“追加一行”按钮，但默认不追加。

### 4. 底部固定操作栏

固定在页面底部：

- 主按钮：`提交可录入 X 条`
- 次按钮：`清空已完成`
- 异常按钮：`查看异常 Y 条`

### 5. 异常区独立

异常不要混在正常清单里影响效率，建议：

- 默认折叠异常区。
- 有异常时显示红色角标。
- 点击展开查看。

## 信息架构建议

### 清单行状态

| 状态 | 颜色 | 可提交 | 操作 |
|---|---|---|---|
| 待接收 | 蓝色 | 是 | 改数量、删除、详情 |
| 待发出 | 绿色 | 是 | 改数量、删除、详情 |
| 仅查看 | 灰色 | 否 | 详情、删除 |
| 异常 | 红色 | 否 | 重试、删除、详情 |
| 提交中 | 橙色 | 否 | 不可编辑 |
| 已提交 | 浅灰/绿色 | 否 | 清理、详情 |

### 操作员最少认知字段

清单行只显示这些：

1. 动作：接收/发出
2. 工序：第几道 + 名称
3. 可用数量
4. 本次数量
5. 异常原因

不要在主清单里堆太多技术字段。

## 建议分三阶段落地

### 第一阶段：交互骨架优化

- 页面改为扫码清单模式。
- 扫码后新增行。
- 默认填可用数量。
- 支持改数量、删除。
- 支持统一提交。

### 第二阶段：现场效率优化

- 重复扫码定位与闪烁。
- 成功/异常音效或震动。
- 异常区折叠。
- 提交失败单行重试。
- 数量 `- / + / 全部` 控件。

### 第三阶段：手机扫码体验优化

- 相机连续扫码稳定性优化。
- 暂停/继续扫码。
- 手电筒按钮。
- 拍照/相册识别。
- 弱网/相机权限异常兜底提示。

## 需要修改的主要文件

预计只涉及前端为主：

- `frontend/src/views/ScanPage.vue`：核心页面重构。
- `frontend/src/api/records.ts`：如现有接口够用则不改；如需批量提交接口再扩展。
- `scripts/validate_scan_cart_ui.py`：补充交互契约验证。
- `scripts/human_ui_traversal.py`：补充页面元素和流程验证。

后端暂不建议改，先复用现有：

- `GET /api/records/scan/judge`
- `GET /api/records/detail/{record_id}`
- `POST /api/records/receive`
- `POST /api/records/ship`

## 验收标准

### 页面体验验收

- 扫码后不跳页。
- 连续扫 5 个码不卡顿。
- 每个有效码生成一行。
- 默认数量正确。
- 数量可改。
- 行可删。
- 手机扫码入口可见。
- 拍照/相册入口可见。
- 异常码不阻断继续扫码。

### 自动化验证

- `npm run build` 通过。
- `python3 scripts/validate_scan_cart_ui.py` 通过。
- `python3 scripts/human_ui_traversal.py` 通过。

### 业务验证

- 接收码提交后 DB 接收批次增加。
- 发出码提交后 DB 发出批次增加。
- 超量录入被拒绝。
- 无权限记录不可提交。
- 已提交成功项不重复提交。

## 风险与取舍

1. **真实手机相机依赖 HTTPS/权限**  
   本地 HTTP 下部分浏览器可能禁止摄像头，需要部署环境或内网 HTTPS 验证。

2. **统一提交不是原子事务**  
   当前复用单条 receive/ship API，可能出现部分成功、部分失败；页面必须明确展示每行结果。

3. **重复扫码策略需确认**  
   默认建议同码不新增行，定位已有行；如果现场确实需要同一记录多批次录入，则需增加“允许重复行”开关。
