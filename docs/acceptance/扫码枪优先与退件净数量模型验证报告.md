# 扫码枪优先与退件净数量模型验证报告

生成时间：2026-06-12 00:20

## 结论

本轮围绕两个业务优先级完成开发与验证：

1. **扫码枪录入优先**：已从“相机扫码优先/手动兜底”调整为“扫码枪单次录入 + 批量扫码解析优先”，适配厂家操作员手持或固定扫码枪现场作业。
2. **退件逻辑重构**：已从“直接核减接收/发出累计数量”调整为“退件独立流水 + 有效数量折算”，避免历史接收/发出批次被改写造成对账混乱。

**验证结论：通过。**

---

## 一、查阅开发文档后的问题确认

旧文档和实现中，退件逻辑为：

- 创建 `ReturnRecord`
- 发送方 `total_ship_qty -= return_qty`
- 接收方 `total_receive_qty -= return_qty`
- 状态通常不回退

该模式的问题：

- 历史发出/接收批次仍然存在，但累计字段被扣减，批次汇总与主表累计不一致。
- 退件后重发/重收时，无法清楚区分“历史毛数量”和“当前有效数量”。
- 现场对账时容易出现“明明扫过/发过，累计数却变少”的理解混乱。

## 二、新业务逻辑设计

### 2.1 数量口径

| 口径 | 含义 | 来源 |
|---|---|---|
| 毛接收量 `gross_receive_qty` | 历史所有接收批次累计 | `process_records.total_receive_qty` |
| 毛发出量 `gross_ship_qty` | 历史所有发出批次累计 | `process_records.total_ship_qty` |
| 退入量 `returned_in_qty` | 本记录作为接收方，退回上道的数量 | `return_records.to_record_id` 汇总 |
| 退出量 `returned_out_qty` | 本记录作为发送方，被下道退回的数量 | `return_records.from_record_id` 汇总 |
| 有效接收量 `current_receive_qty` | 当前业务有效接收量 | 毛接收量 - 退入量 |
| 有效发出量 `current_ship_qty` | 当前业务有效发出量 | 毛发出量 - 退出量 |

### 2.2 新退件原则

退件不再直接改写历史累计数量：

- `receive_batches` 保留原始接收事实。
- `ship_batches` 保留原始发出事实。
- `return_records` 作为独立退件凭证。
- 当前业务可用量统一由退件流水折算。

### 2.3 后续业务约束

- 下道可接收量 = 上道有效发出量 - 本道有效接收量。
- 本道可发出量 = 本道有效接收量 - 本道有效发出量。
- 订单完结判断 = 所有工序有效发出量达到订单总量。

## 三、已完成开发项

### 3.1 扫码枪优先

前端 `/scan` 已调整为：

- 默认进入“扫码枪”页签。
- 输入框自动聚焦。
- 支持扫码枪扫入后按 Enter 自动处理。
- 支持重复扫码提示。
- 支持批量粘贴二维码，一行一个或逗号/空格/制表符分隔。
- 相机扫码降级为备用入口，明确提示“工业扫码枪优先”。

后端新增：

- `POST /api/records/scan/batch`
- 入参：`qr_codes: string[]`
- 去重、逐条解析、逐条权限检查。
- 返回成功/失败数量和每条跳转结果。

### 3.2 退件净数量模型

后端新增/调整：

- `_sum_return_qty()`：汇总退件流水。
- `_quantity_snapshot()`：统一计算毛数量、退件量、有效数量。
- `_sync_record_status_by_effective_qty()`：按有效数量同步状态。
- 接收校验改用上道有效发出量。
- 发出校验改用本工序有效接收/有效发出量。
- 退件接口只新增退件流水，不直接扣减 `total_receive_qty/total_ship_qty`。
- API 响应新增：
  - `gross_receive_qty`
  - `gross_ship_qty`
  - `returned_in_qty`
  - `returned_out_qty`
  - `current_receive_qty`
  - `current_ship_qty`
  - `available_receive_qty`
  - `available_ship_qty`

## 五、边界说明

- `total_receive_qty/total_ship_qty` 当前继续作为历史毛累计字段保留，避免破坏旧接口兼容。
- 退件后重发会使毛发出量大于订单量，这是正常的历史流水现象；业务判断必须使用 `current_*` 有效数量字段。
- 前端核心页面后续应统一展示“当前有效数量”为主，“历史毛数量/退件量”为辅助明细。
- 相机二维码自动识别库仍未接入；当前优先解决的是厂家现场扫码枪单次/批量录入。
